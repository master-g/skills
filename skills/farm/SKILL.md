# farm — 把活派给便宜的 worker

orchestrator（当前模型）只做四件事：计划、写 brief、定验收门禁、独立复验。
worker 只做一件事：按 brief 实施并写报告。

任务已有方案或明确目标才派发。没有就先规划，farm 不做探索。仅分析或编辑 farm 不代表要启动 worker。

流程六步，顺序固定。本文件写每一步的语义和完成标准，与宿主无关；具体工具和命令在第 1 步选定的后端文件里。

## 1. 检测环境与能力

依据本次会话实际提供的工具列表和模型列表作答。宿主或 GUI 的名称本身不证明支持派发。

先确定环境：GUI App，还是终端里的代理 CLI。再确定能力：后端要提供下面四个动作，逐个找到本会话里对应的工具或命令。

| 动作     | 含义                                          |
| -------- | --------------------------------------------- |
| 启动     | 起一个 worker，指定它的模型，把 prompt 交给它 |
| 完成信号 | 得知 worker 已结束                            |
| 取现场   | 报告缺失时拿到 worker 的原始输出              |
| 修正     | 把修正内容发给同一个 worker，让它接着做       |

按第一条成立的选定后端，读对应文件，后续每一步的动作都用它给出的工具和命令：

1. 用户明确要求在 pane 里看 worker 实时运行、随时插手 → [CLI 后端](references/cli-worker.md)。
2. 会话有原生子代理工具 → 原生后端。Claude Code（Agent 工具）读 [Claude Code 原生 worker 用例](references/claude-code-worker.md)；Codex 桌面 App 等 GUI（`spawn_agent`）读 [App 原生 worker 用例](references/app-worker.md)。其他宿主没有专门文件：从它的工具说明里找出四个动作，后续各步按本文件执行。
3. 没有原生子代理工具 → [CLI 后端](references/cli-worker.md)。

完成标准：环境、后端、四个动作各用什么工具或命令都已确定。「启动」或「完成信号」找不到就报告缺什么（工具 / CLI / 配置），停止。「修正」找不到时，返工改为把修正内容追加进 brief、重新启动一个 worker。

## 2. 通信

orchestrator 与 worker 之间只靠两个文件和一句 prompt，所有后端相同：

- 下行是 brief：`.farm/<task>-brief.md`，worker 需要知道的一切都写在里面。
- 上行是报告：`.farm/<task>-report.md`。worker 的口头回复和最终消息只是自述，不算结果。
- worker 的 prompt 永远是同一句：`读 <$PWD/.farm/<task>-brief.md> 并执行,报告按其中要求落盘`。
- 修正也走 brief：把门禁的失败输出写成修正 brief，用后端的「修正」动作发给同一个 worker。
- worker 之间不通信。子任务靠互不重叠的文件边界隔离，需要协调的事由 orchestrator 写进各自的 brief。

brief 模板：

```markdown
# <task>

## 目标

<一句话>

## 背景与相关文件

<路径 + 各一句为什么相关>

## 边界

可改:<...>;不可改:<...>

## 验收命令

<一条可执行命令,退出码 0 = 通过>

## 报告

把结果写入 .farm/<task>-report.md:完成了什么 / 改动文件列表 / 验收命令输出 / 未决问题。

## 停止条件

验收命令连试 2 轮仍不过,或需要超出边界的改动 → 把现状写进报告并停止。
```

## 3. 拆分、并发数与确认

### 拆分与并发数

把任务拆成 k 个子任务。子任务同时满足三条才成立：负责的文件与其他子任务互不重叠；有只覆盖自己范围、可单独运行的验收命令；不依赖其他子任务的产出。拆不出来就合并，k = 1 走单 worker 流程。

并发上限 N 来自用户参数 `-j N`（“并发 3”“4 个 worker”等说法同样算；`-j 1` 即串行）：

- 给了参数：参数即授权，不再问是否并发，取 min(N, k)，在确认屏用一行说明取值。
- 没给参数：k = 1 不问；2 ≤ k ≤ 4 问“并发 k 个 / 串行”；k > 4 问“同时最多 4 个（推荐）/ 自定义数量 / 串行”。4 是可见 pane 里同时等审批、人还盯得住的上限。

这个问题并入下面的确认屏，一屏答完。k ≥ 2（含串行）时，派发与门禁按 [worker 池](references/pool.md) 执行。

### worker 模型

用户点名的模型优先。否则从 pairs 取：运行本技能目录（与 SKILL.md 同目录）下的 `preflight.sh`，读 JSON 的 `pairs`（用户配置 `~/.config/farm/pairs` 优先，否则技能自带默认）。你知道自己是谁（host + 模型名）：按 精确项 → `<host>:*` → `*` 的顺序取第一个匹配。无匹配且无 `*`：列出全部 pairs 让用户选。后端文件自带模型分工的，按后端文件。

指定的模型在本会话不可用时，说明缺什么让用户选，不静默换模型或换后端。

### 确认屏

一次列清：后端、worker 模型及其来源、并发问题（需要问时）、将启动的每个 worker（子任务、模型、运行位置）。一次确认覆盖屏上列出的全部启动。

每次实际调用外部模型都遵守当前环境与用户的授权边界；模型选择不代替调用授权，修正轮次需要新进程时也一样。

### 红线

无头 worker 只允许 **pi**（用户调用本技能即接受 pi 无头改文件）。claude / codex CLI 当 worker 只能在 herdr pane 里跑，审批弹窗必须用户可见。宿主自带的原生子代理不是外部 CLI 进程，不受这条限制，按对应后端文件执行。

## 4. 派发与等待

1. 核对项目目录与未提交改动，按上面的模板把 brief 写到 `.farm/<task>-brief.md`。
2. 用后端的「启动」动作派发。
3. 等后端的「完成信号」，不猜结果。等待期间 orchestrator 不改 worker 负责的文件。

完成标准：brief 已落盘，且按后端文件的判据确认 worker 已启动。整个任务必须完成第 5 步的独立验收。

## 5. 门禁

worker 结束后逐个过门禁：

1. 读 `.farm/<task>-report.md`。报告缺失：用后端的「取现场」动作拿到 worker 输出，判断 worker 是死了还是违约，显式报告给用户。
2. 看负责范围内的实际 diff。
3. **独立重跑验收命令**，不信 worker 自述。

每个子任务据此落到三种状态之一：

- 通过：验收命令退出码 0，diff 在边界内。
- 返工：把失败输出写成修正 brief，用「修正」动作发给同一个 worker，再过一次门禁。**最多 3 轮**。
- 升级：3 轮仍失败，或需要超出 brief 边界的改动。保留现场，带报告与门禁输出交给用户。

k ≥ 2 时，逐个审计之后还有集成门禁，见 [worker 池](references/pool.md)。

## 6. 汇报与下一步

向用户汇报：

- 每个子任务的状态（通过 / 升级）和用掉的修正轮次。
- 改动摘要（git 仓库用 `git diff --stat`）和门禁的实际输出。
- 限制：没运行的检查、worker 报告里的未决问题。
- 下一步建议：只列本次结果直接引出的事项，例如升级项需要用户决定什么、通过的改动是否提交、方案里还没派发的部分。

代理创建成功、worker 自述完成都不等于验收通过。后端有收尾动作的（如关闭 pane），按后端文件执行。

## 失败处理

任何一步失败都显式说明：哪一步、为什么、现场在哪（log / 报告 / pane 名 / agent ID）。不静默重试，不替 worker 宣布完成。

建议把 `.farm/` 加入项目 `.gitignore`。
