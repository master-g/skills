我不确定现在走到哪了、接下来该干什么。先盘点，再评估，最后给建议。只做评估与规划，输出后停下等我选。

## 1. 盘点证据

三类来源，前两类自己读，第三类按体量分流：

- **本会话** —— 对话历史与当前上下文：用户提出的目标、已经做过的操作、已验证与未验证的结论。
- **仓库状态** —— `git status`、`git log --oneline -20`、当前分支；有未提交改动时看 diff 摘要。
- **进度记录** —— 工作目录下的 `PROJECT_MEMORY.md`、`MEMORY.md`、`TODO.md`、`PLAN.md`、`NOTES.md`、`CHANGELOG.md`，以及 `CLAUDE.md` / `AGENTS.md` 中链接或描述的任何进度记录（「上次会话」「下次运行」「待办」之类的段落及其指向的文件）。`CONTEXT.md` 存在时用它的统一语言。
  - 先 `wc -l` 数这些文件合计行数。合计约 300 行以内：直接通读。
  - 超过：派一个子代理处理这一类，主对话不读原文。给子代理的任务：通读全部进度记录，对照 `git log --oneline -50` 与 `git status`，只盘点、不规划，返回结构化摘要 —— 各文件存在性与角色；目标（引记录原话）；已完成条目 + 证据出处；进行中 / 卡住；声称完成但证据缺失的条目；记录之间的矛盾。每条注明文件与小节。
  - 主对话只保留摘要。仅当摘要某条与 git 状态或会话明显冲突时，定点复查该条对应的原文，不整文件回读。

**完成条件**：三类来源各自有结论 —— 读到了什么（或拿到了摘要），或明确写出「不存在」；子代理路径下，摘要中每条声称完成的事项都带证据或明确标为「未验证」。

## 2. 状态评估

把盘点结果压成一张状态表：

- **目标** —— 这段工作到底要达成什么。以用户原话为准；记录与对话不一致时，选更新的那个，标记另一个待更新。
- **已完成** —— 每条附证据（commit、文件、测试输出、对话中的确认）。
- **进行中 / 卡住** —— 停在哪一步，卡在什么上。
- **未验证** —— 记录里声称完成但找不到证据的（memory 说做完了，git 里没有；对话里说测试通过，没看到输出）。单独列出，与「已完成」分开。

**完成条件**：每一条都带证据出处，或明确标为「未验证」。

## 3. 第一性原理规划

放下记录里原有的计划，从目标本身反推：

1. 目标达成需要哪些事实为真？
2. 其中哪些已经为真（有证据），哪些还没有？
3. 剩下的里，哪一件最大程度地消除不确定性或解除阻塞？

给出 1–3 条下一步，按顺序排列。每条写清：**做什么**（动词开头的具体动作）、**为什么先做它**、**完成标志**。建议只描述要做的事，不点名工具或技能。原计划与反推结果不一致时，说明差异，推荐反推的那个。

## 4. 输出并停下

按「现状 → 未验证与分歧 → 下一步」三段输出，总长控制在一屏内。输出后停下，等用户选定再动手。
