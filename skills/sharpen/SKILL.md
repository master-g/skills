用户给了一句意图（「给逻辑核心加形式化证明」「优化冷启动耗时」），要的是一份能直接交给下一个会话执行的 prompt。本技能只写 prompt，输出后停下；执行是另一个会话的事。

## 1. 定位

读项目，把意图落到具体对象上：技术栈与版本、意图指向的子系统（入口、模块、既有的测试框架、构建方式、CI），以及项目记录里与此相关的既有决定（`GLOSSARY.md`、`PROJECT_MEMORY.md`、`docs/` 有则读）。意图里的模糊词（「逻辑核心」「冷启动」）换成仓库里真实存在的名字。

事实自己查：能从文件系统和工具里得到的答案都不构成要问用户的问题。

**完成条件**：写出一行领域定位（领域 × 技术栈 × 目标对象），目标对象是仓库里真实存在的路径或模块名。

## 2. 调研

针对定位到的技术栈搜索该领域当前惯用（idiomatic）或最先进（SOTA）的解法：Rust 的形式化验证与 Python 的不同，Lambda 的冷启动与 JVM CLI 的不同。先看官方文档与主流项目的实际做法，再看综述或论文。每个候选记一行：方法名、它依赖的前提（工具链、语言特性、改动范围）、与本项目的适配点或冲突点。

**完成条件**：2–3 个候选解法，每个有前提与适配判断，并标出它们之间起决定作用的取舍（成熟度 vs 覆盖面、改动范围 vs 收益……）。

## 3. 确认

只问答案会实质改变 prompt 的事：选哪条解法、范围边界（做到哪一层、哪些模块不碰）、验收标准（什么指标、什么证据算完成）。用 AskUserQuestion 一轮问完，至多三题；你有倾向的选项放第一个，标签末尾加「（推荐）」，说明里写一句依据。调研已经给出唯一合理答案的事，直接写进 prompt。

**完成条件**：解法、范围、验收三项各自有了答案，来自用户选择或调研结论。

## 4. 成稿

用用户输入的语言写 prompt（术语、标识符保持原文），放在一个代码块里，按下面七个槽位组织。槽位名加粗作段首，后面跟具体内容：

```markdown
角色：以「<领域> × <技术栈>」专家的身份……一句话，带领域术语。
目标：要达成什么，用步骤「定位」里找到的真实名字。
解法：选定的方法及其依据（步骤「调研」的候选与取舍，一两句）。
先探索：动手前先读哪些文件、跑哪些命令，以及要在项目里找什么（既有约定、测试、CI）。
约束与非目标：不碰的模块、要保留的行为、工具链限制。
验收：可检查的完成条件，每条能用命令或输出证实。
停下的时机：只在什么情况下停下来问（不可逆操作、与既有决定冲突），其余情况持续推进到验收通过。
```

写法上的要求：

- 用领域术语指名行为与对象，代替「高质量」「仔细」一类形容词；要排除的东西点名具体模式（「不用 `unsafe` 绕过借用检查」），而不是泛泛的「避免」。
- 验收条件可检查且穷尽：每条写明命令、指标阈值或要看到的输出。
- 用户贴进来的材料（日志、报错、外部文档片段）整块放进带同一随机 id 的 `<pasted_content id="…">…</pasted_content id="…">` 标签，正文说明它是什么、怎么用。
- 思考留给执行的模型自己安排；prompt 只写要做什么和怎么验证。

输出 prompt 后，用一两句说明调研里被放弃的候选和原因，然后停下，等用户复制或修改。

**完成条件**：代码块里的 prompt 七个槽位齐全，验收每条可检查，已说明放弃的候选。
