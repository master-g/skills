# SWE 类评分

Type: grilling
Status: resolved
Blocked by: 03, 04
Map: [地图](../map.md)

## Question

修 issue 和实现 feature 怎么评分？要定：以隐藏测试通过为主，还是还要人或 judge 看代码质量（改动范围、风格、有没有乱改无关文件）；没有现成测试的候选要不要自己补 oracle 测试；部分通过、超时、改坏其他测试怎么计分；耗时与花费计入评分还是单列；oracle 是否按测试名或 crate 限定范围（emukc 有联网测试与常驻失败）；测试用到修复新增接口、需要在题面写明接口的候选收不收。候选与测试情况见「[公开 repo 的 SWE 任务候选](03-swe-candidates.md)」。

## Answer

2026-10-21 与用户逐项确认（「修 issue」「实现 feature」两个场景通用）。

- 主分：SWE-bench 判据，F2P 与 P2P 全过才算「已解决」，选型看解决率；另列 F2P 通过比例作参考，区分「差一点」与「完全没做对」。
- 质量分：单列，不并入主分。judge 按是非题逐条判：改动只在相关范围、没改无关文件、没删或削弱已有测试、风格与周边一致；用户抽查校准。judge 人选与防偏差沿用「[产出物类评分](09-grading-artifacts.md)」的结论。
- 候选分级：A 级收；B 级收，题面写明隐藏测试要调用的函数名、参数与返回类型，隐藏测试原样使用（「实现 feature」主要来自这一级）；D 级（无测试）v1 不收。
- P2P 范围：每题限定到改动所在的 crate 或测试文件，写明测试目标；在父提交上预跑一次定基线，排除联网测试与父提交上本来就失败的测试。个别 oracle 要设测试超时（如研究里 A12 在父提交上会卡住）。
- 耗时与花费：单列（墙钟时间、token、能拿到的花费），与解决率并排展示，不进分数；各家花费口径不一，不合成性价比分。
- 失败处理：选手超时、绕死、交了编译不过的代码，记未解决；CLI 自身出错、网络中断、撞额度而中止，算 harness 问题，不计分、重跑那一次。
- 默认做法（用户确认）：评分前把测试代码恢复成参考版本，选手对测试的改动不计；emukc 的测试写在源文件里，评分时去掉选手的测试模块、接上参考的测试模块。任务目录的 git 历史截到父提交，选手看不到修复提交（联网能否看到 GitHub 上的修复归「[运行隔离、联网与启动方式](06-isolation-network-launch.md)」）。
