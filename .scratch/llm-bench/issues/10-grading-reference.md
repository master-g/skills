## Question

代码审查和代码库问答有参考答案，怎么评分？要定：代码审查用预埋缺陷的 diff 算查全与查准，还是用历史上真实被修过的缺陷；误报怎么扣分；问答的参考答案由谁写，评委按要点对照打分还是人评；答案里的证据（文件、行号）是否要求可核验。

补充：评审团（三家族多数票）、用户盲抽查校准、评委与 rubric 版本钉死后全量重评，已在「[产出物类评分](09-grading-artifacts.md)」定下，这里沿用，只定参考答案类特有的部分。

## Answer

2026-10-21 与用户逐项确认。评审团、盲抽查、版本钉死与额度上限沿用「[产出物类评分](09-grading-artifacts.md)」；结果并列耗时与 token。

代码审查：

- 题目来源：真实缺陷。把后来被修掉的缺陷追溯到引入它的提交，截到缺陷所在文件加几段邻近改动，约 200 行内，不暴露缺陷位置；选手在该提交的仓库里审查，可以读上下文。不用预埋缺陷：预印本里合成缺陷最好的 F1 是 0.847，拉不开差距。排除作者在 PR 正文「Not done / Not modelled」里声明过的项，题面不给 PR 正文。
- 计分：选手按严重度排序列出发现；主分是已知缺陷在前 5 条里的命中率（CRBugBench 的做法，多写条数刷不了分）。评审团再逐条判其余发现是否站得住，站不住的计误报、单列误报率；站得住但不在已知缺陷里的不扣分，因为已知缺陷不是 diff 里的全部问题。
- 格式与匹配：提示词规定每条发现写位置（文件:行）、问题、后果、严重度，按严重度排序；不显式调用审查类技能。评审团判「是否描述同一个底层问题」，措辞不同不扣分，位置指到同一函数即可。
- 候选（2026-10-21 子代理在父提交上 `git blame -w -M -C -C` 追溯，未逐条人工核对；编号沿用「[公开 repo 的 SWE 任务候选](03-swe-candidates.md)」）。排除测试、golden 数据、lock 与文档后，不超过 150 行且缺陷在 diff 里看得见的只有前两条，其余要截取：

代码库问答：

- 题目与参考答案：代理读代码起草，每个要点附文件与行号证据并在任务提交上核实；用户逐题审定后冻结。
- 评分：参考答案拆成「必须提到的要点」与「不该出现的说法」两类是非题，评审团逐条判，得分为通过占比。
- 证据：答案的每个论断必须引用文件与行号；harness 在任务提交上核对引用存在，不存在的单列失效引用数；「引用支撑论断」作为一条是非题，评审团对照 harness 抽出的代码片段判。
