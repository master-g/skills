# show-me-html 构建耗时分析与优化交接（2026-10-22）

## 结论

一页 `status-report` 报告从调用 `/show-me-html` 到交付用了 32 分钟，其中 20.5 分钟（64%）在等 `build.py` 里的无头 Chrome。构建本身（内联资产 + 文本检查）只要 0.13 秒，慢的全是渲染检查和 `--snap`：

- **通用原因**：一次 `build.py --snap` 冷启动 Chrome 11 次（渲染检查 3 次，快照 8 次），每次都是全新 profile，光启动加空页就要 3.8 秒。
- **本机特有原因**：Chrome 不读 `HTTP(S)_PROXY` 环境变量，本机系统代理是关的，每次启动都要直连 Google Fonts 拉字体。单次渲染因此从 4 秒拖到 12～69 秒，同样的构建一次 23 秒、一次 67 秒，带快照的一次 69 秒、一次 270 秒。
- **原型实测**：只开一个 Chrome、走 CDP 做同样的 3 次探针加 4 张截图，耗时 20.8 秒（字体照常加载，同一实例内只拉一次），屏蔽字体后 8.9 秒。现状是 119.8 秒。

另一半时间花在返工上：第一次构建后又做了 7 轮"改 → 重建 → 截图 → 看图"，其中 5 轮出在表格和图表布局上，技能本可以事先避免或在构建时报出来。还有一个缺陷（图表行尾文字超出 viewBox 被裁）构建和眼检都漏掉了，事后才发现。

按实测节省排序的建议在文末。最大的一项是让 `build.py` 用单个 Chrome 实例跑渲染检查和快照，预计把这次会话的构建等待从约 20 分钟压到 3 分钟左右。

**后续**：这些建议已写成计划 020–029（`plans/README.md`「show-me-html 构建耗时」），2026-10-23 全部合入；建议 2 选了 (a) 代理透传，建议 11 未采纳。单实例 CDP 的正式实现是 `skills/show-me-html/scripts/cdp.mjs` 与 `render.mjs`，本文的 `cdp-bench.mjs` 是它之前的原型，正文保留写作时的状态。

- **页面**：一页 Android 多语言缺失报告，配方 `status-report`。内容包括指标带、一张通栏 F5 刻度行（741 根刻度）、四张表（其中一张是 520 行明细，带 5 个筛选控件）、两个折叠块，成品 389 KB。页面主题与本分析无关，这里不写项目名。

- **"模型时间"是残差**：用阶段总时长减去工具耗时得到，包含生成、思考和网络往返，不是直接测量值。

- **局限**：只有一次会话一个页面的样本。字体卡顿取决于网络环境，换一台系统代理开着的机器可能不明显；11 次冷启动的开销则在任何环境下都存在。

## 构建耗时拆解

在同一个 389 KB 页面上逐项测得：

| 测量                                                                                            | 结果                            |
| ----------------------------------------------------------------------------------------------- | ------------------------------- |
| `build.py --no-render`（内联 + 文本检查）                                                       | 0.13s                           |
| `build.py`（加 500/1024/1280 渲染检查）                                                         | 18.2～33.6s（同一页面两次实测） |
| `render_check` 只跑 500 / 只跑 1280（字体直连）                                                 | 12.8s / 69.1s                   |
| 同上，但先删掉页面里的 Google Fonts `<link>`                                                    | 4.1s / 3.9s                     |
| 只有一行字的空页面，Chrome 冷启动 + `--dump-dom`                                                | 3.8s                            |
| 带探针的单次 `--dump-dom`：默认 / 加 `--proxy-server` / 加 `--host-resolver-rules` 屏蔽字体域名 | 16.7～18.7s / 5.3～7.3s / 4.1s  |
| `build.py --snap` 全流程（现状）                                                                | 119.8s                          |
| 单实例 CDP 原型（`cdp-bench.mjs`）：3 次探针 + 4 张整页截图，字体直连 / 屏蔽                    | 20.8s / 8.9s                    |

**慢在哪里**：`render_check` 每个宽度起一次 Chrome（`--virtual-time-budget=4000`，探针自己再 `setTimeout` 1500ms）。`snap_page` 对 light/dark × 500/1280 各起两次：一次 `--dump-dom` 量页高和导出 Markdown，一次 `--screenshot`。全新 profile 没有缓存，每次都要重新请求 Google Fonts；思源宋体被 Google 切成上百个 unicode-range 分片，中文页面要拉很多个。从实测看，`--virtual-time-budget` 会等挂起的网络请求结束，所以字体请求慢多少，这次启动就慢多少：删掉字体 `<link>` 后单次回到 4 秒左右。

**原型说明**：`cdp-bench.mjs` 只用 Node 内置 WebSocket（与 `scripts/probe_round.mjs` 同样的连接方式），在一个实例里依次做三件事：

1. 3 个宽度各加载一次带 `PROBE` 的页面，读到 `PROBE|` 标题为止；
2. 用 `Emulation.setEmulatedMedia` 设 reduced motion，用 `addScriptToEvaluateOnNewDocument` 注入主题；
3. 按 `scrollHeight` 设视口后截图。

核对过 4 张截图里图表 748 条线（741 根刻度加 7 条基线）都画出来了。不设 reduced motion 时截到的是入场动画中途，这一点移植时必须保留。字体直连时，只有第一次加载要等字体（14s），后面每次 1.7s。

## 其他摩擦

- **快照是整页长图**：1280 宽高 5840px，500 宽 16483px，截到 16000px 就截断了。Read 工具会下采样长图，读不清细节，只能在外面切片：`sips -c --cropOffset` 的偏移行为和预期不符，切出来的段是乱的；Python 没装 PIL；最后用 `magick` 切，16000px 的图要 21 秒。500px 的页尾（建议动作、口径两节）超过 16000px，窄屏下一直没被眼检过。
- **小修也要全套重拍**：`--snap` 固定拍 4 张，并且每次都先把 3 个宽度的渲染检查跑一遍；`snap_page` 在 500/1280 又各跑一次探针，和渲染检查重复。没有"只拍 light 1280"或"只拍某一节"的选项。SKILL.md 允许"小修检查受影响行为"，但工具层面没有对应的快捷路径。
- **交互验证没有内置手段**：技能只写了交互"需真实浏览器"，于是加载 ego-browser 技能、读 550 行指南，又踩了两个坑：选择器同时命中两个元素报歧义，`finish()` 必须写成 `{ keep: [] }`。图表要滚进视口才画（`reveal`），第一次断言得到 0 根刻度。`probe_round.mjs` 已经有按键、筛选和打印的原语，但只服务 5 个冻结场景页。
- **Markdown 导出丢数据**：数据图在导出里只剩图头和图注，SVG 的 `<title>`/`<desc>`（这页写了每种语言的数字）没导出。
- **读文档**：为一张 F5 读了 `charts.md` 全文和 gallery 的三段渲染块。残差 10.7 分钟里约 2.6 分钟在这一步，比构建等待小一个量级。

## 优化建议

按这次会话里实测或可估算的节省排序。落点按 `MAINTENANCE.md` 的纠正路由：可机械核对的进 `build.py`，可复用视觉进 `show-me.css`，判断类进 `references/*.md`。

1. **`build.py` 用单个 Chrome 实例跑渲染检查和快照**（落点：`scripts/build.py`，属于 harness）
   - **改法**：起一次 `--headless=new --remote-debugging-port=0`，用 CDP 设视口、主题注入、reduced motion，再依次加载、读探针结果、截图。Python 标准库没有 WebSocket 客户端，可以像 `compile_math` 调 `math.mjs` 那样，由 `build.py` 调一个 Node 脚本；连接代码直接复用 `probe_round.mjs`，原型见 `cdp-bench.mjs`。找不到 Node 时退回现在的多次冷启动。
   - **收益**：`--snap` 从 119.8s 降到约 21s；只做渲染检查约 6～8s（原来 18～34s）。按这次会话算，8 次带快照的构建从 1076s 降到约 170s，3 次普通构建从 153s 降到约 25s，合计省下约 17 分钟。
   - **注意**：现在靠 `--virtual-time-budget` 等页面稳定，改成真实时间后要显式等 load 事件加探针标题。截图视口要按 `scrollHeight` 设，并保留 reduced motion，否则会截到动画中途。顺带一提，`PROJECT_MEMORY.md` 里候选的 `--pdf` 在 CDP 下就是一次 `Page.printToPDF`。

2. **字体在检查里怎么加载**（需维护者决定；落点：`scripts/build.py`）
   - **做了建议 1 之后**：一个实例里字体只拉一次，影响从"每次启动 12～69s"降到"每次构建多十几秒"（20.8s 对 8.9s）。
   - **(a) 环境变量里有代理时给 Chrome 加 `--proxy-server`**：几何按真实字体量，但依赖代理配置。
   - **(b) 检查时屏蔽 `fonts.googleapis.com`/`fonts.gstatic.com`**：最快，几何按兜底字体量，相当于中国大陆读者看到的样子；但截图字体和用户实际看到的不同，计划 017/019 的阈值又是在真实字体下标定的。
   - **(c) 不处理，只做建议 1。**

3. **快照与渲染检查共用探针，`--snap` 能缩小范围**（落点：`scripts/build.py` + `compose-and-check.md` 的眼睛关一段）
   - **合并探针**：500/1280 两个宽度的结果由渲染检查一次产出，快照不再重跑探针。
   - **缩小范围**：加 `--snap-theme light|dark|both`、`--snap-width 500,1280` 一类参数，默认仍是 4 张；文档写明"小修只拍受影响的宽度和主题"。
   - **收益**：在建议 1 之后，每次小修再省一半左右；不做建议 1 时，每少拍一张省两次冷启动（约 25～40s）。

4. **快照按视口高度切片输出，并标出每片对应哪一节**（落点：`scripts/build.py`）
   - **改法**：输出 `light-1280-01.png`、`light-1280-02.png` 这样的切片（CDP 的 `captureScreenshot` 带 `clip` 就能切），每片高度控制在读图时不被明显降采样的范围（这次实测 1280×1500、500×1600 读得清）。同时打印"切片 → 所含 h2"的对照表，小修后只重读受影响的那一两片。
   - **顺带**：16000px 的截断不再存在，窄屏页尾也能被看到。
   - **收益**：省掉切图步骤（这次 22s 加几次试错）和读无关切片的 token，也让眼检能发现建议 6 那类细节问题。

5. **表格里的长标识符**（落点：先改 `references/components.md`「表格」，是否动 `show-me.css` 由维护者定）
   - **问题**：`code, .kbd { overflow-wrap: anywhere }` 会把 min-content 缩到一个字符，多列表格里装 snake_case key 或模块路径时，标识符被压成竖条。这次 7 轮返工里占了 4 轮（12:00、12:04、12:07、12:10）。
   - **历史**：计划 012 否决过全局调整表格密度，理由是"四页 390px 都不横滚"。这里是更窄的一种情形：多列表格加长标识符。
   - **(a) 只改文档**：标识符列在 `_`、`/` 后插 `<wbr>`，标识符列设 `min-width`，长文本列设 `max-width`。这正是这次最后的修法。
   - **(b) 改 CSS**：`.table code { overflow-wrap: break-word }`。`break-word` 不改 min-content，列宽至少容下最长的标识符，窄屏改为表格局部横滚，等于改变了 012 的取舍。
   - **(c) 加 WARN**：在 `PROBE` 里量表格单元格内 `code` 的渲染宽度，小于约 4 个字符宽时报"标识符被压成竖条"。

6. **`build.py` 探针查 SVG 文字越出 viewBox**（落点：`scripts/build.py` 的 `PROBE`）
   - **改法**：把 `gallery.py` 的 `PROBE` 里「文字重叠与越界」那段的越框部分搬进来，任何 `svg text` 的 bbox 超出 viewBox 就报。
   - **证据**：这次 F5 行尾文字被裁，构建和眼检都没发现。
   - **级别**：建议 WARN 起步，复现第二次再升 ERROR（毕业规则）。

7. **侧栏和通栏图的冲突写进 layouts.md**（落点：`references/layouts.md`「报告节律」）
   - **规则**：一句话即可——`.with-rail` 的主栏只放正文、窄表和半宽图；`.fig.wide` 与宽表放在 `.with-rail` 之外，口径侧栏放到不含宽证据的那一节。
   - **配套**：计划 019 的下限 0.8 能抓到这次约 0.75 倍的情况，019 照原计划执行即可。0.75 是从截图估的，若要据此调 019 的阈值，先在复现这个布局的页面上实际量 `svg.clientWidth / 800`。另外值得补一条：800 宽通栏图在 500px 下约 0.58 倍，计数类图（F5 这种）该横滚还是另画窄版，目前没有指引。

8. **折叠组件的文档改成与 CSS 一致**（落点：`references/components.md`「折叠」）
   - **改法**：删掉示例里的 `<i data-lucide="chevron-down"></i>` 和"最后一个 svg 会被旋转"那句，改为说明 +/− 由 CSS 画。下拉菜单示例里的 chevron 属于另一个组件，不受影响。

9. **单页交互验证的现成配方**（落点：`scripts/`，加一个单页模式或从 `probe_round.mjs` 抽公共部分；`compose-and-check.md` 交互一段指过去）
   - **改法**：`node scripts/probe_page.mjs 页面.html` 对任意页面做三件事：
     - 列出所有 `select`/`input`/`details`/按钮，并逐个操作一次；
     - 报控制台错误；
     - 截操作前后的切片。
   - **文档补一句**：图表靠 `reveal` 滚入后才画，断言前先 `scrollIntoView`。
   - **收益**：省掉加载第二个浏览器技能和读它的指南（这次约 3 分钟），也让"交互未验证"不再是常态。

10. **Markdown 导出带上数据图的 `<title>`/`<desc>`**（落点：`assets/shell.js` 导出器）
    - 把 `figure svg > desc` 作为图注下方的一段文字导出，复制出去的 Markdown 里数据不丢。

11. **读文档路径**（落点：`references/charts.md` 顶部；优先级最低）
    - 在开头放"编号 → gallery 文件 → 块名"的速查表，用户只要一张已知图型时，不必通读 300 行。这次约 2.6 分钟，比构建等待小得多，可以最后做。

## 预期效果

如果做完 1、3、4，这次会话的 21 分钟构建等待估计降到 3～4 分钟。再加上 5、7、8 提前挡掉的 4～5 轮返工（每轮约 1～1.5 分钟模型时间加一次构建），同样一页预计能在 12～15 分钟内交付。这是按本次样本推算的估计，做完 1 之后应拿同一页面复测。
